# tl;dr

- [dotfiles](https://github.com/officel/dotfiles) を管理しているが、設定がとっちらかるのをどうにかしたかった
- [officel/uchi: Dotfiles Literate Configuration CLI tool.](https://github.com/officel/uchi) を jules を使って書き始めた
- 少しずつ移行しているが、なかなかいい塩梅になってきたので紹介させてほしい（まだ2日目）

# dotfiles

- 言わずと知れた各環境の設定を管理するリポジトリによく付ける名前
- ホームディレクトリの `.` 始まりのファイルなどを管理することから
- 昔からたくさんの管理方法がある

# 課題

- 個人的に各種OSSツールによる dotfiles の管理はオーバースペックすぎると思っていた
- リポジトリでは設定ファイルに必要なものをべた書きしていた（る）
- そのため、いつどうしてソレを入れたのか、なぜ使っているのか、そもそもこれはなんだっけ？となることが増えた
- 他人に紹介しても、このツールは何か、どこでどう設定されているか、どんな情報があるかなどを伝えることが難しい
- 要は自分で管理している情報を、自分でも他人でも簡単に伝えることができない
- いわば現時点での dotfiles は、マシンファーストで必要な設定を詰め込んだだけになっている

# 検討

- [twpayne/chezmoi](https://github.com/twpayne/chezmoi) はたぶんもっともメジャー？
- あきらかにオーバースペックだと思った
- 余計な事はしない、自分で管理するべきところを汚さない、ブラックボックス化させない、等の隠れた好みをもっていた
- いずれのツールも課題を解消することはできそうにない
- じゃあ作るか

# リテレートコンフィギュレーション

- リテレートプログラミングについては、興味があれば各自調べてください
- その思想を設定に持ち込んだのがリテレートコンフィギュレーション
- プログラミング業界的には、アノテーションコメントやドキュメントコメントみたいなもの、で伝わるだろうか
- ドキュメントを書いて情報伝達力を確保しつつ、そこに書かれた内容を設定ファイルとして生成する、ということ

# uchi

- で、作ってみたのが [officel/uchi: Dotfiles Literate Configuration CLI tool.](https://github.com/officel/uchi) ってワケ
- 作ってみたってゆうか、jules の無料枠内でごっそり書いてもらっているだけだけども
- 入力ディレクトリと出力ディレクトリを決めておいて、入力ディレクトリにマークダウンファイルを置いて、出力ディレクトリに設定ファイルを生成する、だけ
- 今のところコードフェンスに書いた内容を抜き出しているに過ぎない
- 生成された設定ファイルを、既存の `.bashrc` 等で読み込めばいい（この辺りは自由が必要だと思ってる）
