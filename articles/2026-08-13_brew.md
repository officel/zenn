# というわけで

- 定期実行やメール通知は個人的には不要だなって
- ざっとコードを見る限り、丁寧な順次処理に見える（順番に brew を実行しているだけに見える）
- エラー処理や丁寧な記録をスルーしていいならタスクで充分なのでは？
- というわけで [feat: brew task](https://github.com/officel/dotfiles/pull/128) 書いた

```yaml
  brew:
    desc: "brew all update"
    silent: false
    vars:
      LOG_FILE: '{{.USER_WORKING_DIR}}/brew_update_{{now | date "20060102"}}.log'
    env:
      HOMEBREW_NO_SANDBOX_LINUX: 1
    cmds:
      - date > "{{.LOG_FILE}}"

      - echo "$ brew update" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew update  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew outdated --formula" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew outdated --formula  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew outdated --cask --greedy-latest" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew outdated --cask --greedy-latest  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew upgrade --yes" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew upgrade --yes  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew cleanup" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew cleanup  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew doctor" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew doctor  1>> "{{.LOG_FILE}}" 2>&1

      - echo "$ brew missing" 1>> "{{.LOG_FILE}}" 2>&1
      -         brew missing  1>> "{{.LOG_FILE}}" 2>&1
```

# 悩ましいところ

- AI に相談してみたんだけど、タスクの外側でログを残す以外に、うまいこと書けなかった
- ごちゃごちゃ書いてて思ったけど、元のリポジトリにログがあるから書いただけで、別にログ要らないならなくてよくね？（今思った
- それはそれとして丁寧なロギングのタスクは欲しいな

## そもそも brew のメンテナンス

- outdated とかはロギングのためってゆうか、バージョン等を見るためにあって、最新化されるだけなら要らないかも？
- 1回流して成功しちゃうともうテストができなくなっちゃうの、brew の使い方がわかってなさすぎた
- やった後に気がついたんだけど、brew を更新すると高確率で Azure CLI ががたがたするのをどうにかしたい

## yaml linter

- ログの話とぶつかるけど、コードを見やすくしたら lint に引っかかった
- ハイフンの後ろに余計なスペースがあると怒られるんだけど、見やすさを取りたい時あるよね
- 面倒だったから手抜きで設定を弱めたんだけど、悩ましい
