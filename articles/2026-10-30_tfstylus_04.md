# 気づきとか覚えたこととかわかったこととか

マインドマップにメモしていたことを吐き出す

## goreleaser

- Golang で開発する時に重宝するリリース自動化ツール？
- タグ打ってpushするだけであとは自動なの楽だなあ
- brew -> homebrew-cask の変更は brew に対しての理解が必要
- changelog の部分は changie とどっちがいいかまだ要検討（未着手）

## golangci-lint

- Golang の静的リンター
- よくばって既存の有名OSSツールの設定を真似たらすごく辛かった
- Go のバージョンによってあるべきが違う？
- まずはデフォルトの最小設定で通して、あとからひとつずつリンタールールを増やして対応（AIが）
- なるべく最初期から入れておいて、AI作業のゲートに加えておくのが大事かも（それはそう）

## homebrew

- 普段は [aqua](https://aquaproj.github.io/) をバージョン管理のメインに使っている
- 作りたての個人開発ツールをインストールして使ってもらうなら素直にビルドしてもらうか brew かってことで
- cask とか formula とか tap とか歴史的経緯とかはよく知らないんだよね
- goreleaser のおかげで設定さえできてしまえばほぼオートでリリースできるの楽
- 一度できるようになれば次からはスムーズ（[uchi](https://zenn.dev/raki/articles/2026-09-06_uchi)も対応してみた）

## VS Code

- AGENTS.md は常に読み込まれるとは限らない？ちょいちょい指示に従わない
- マルチワークスペースのせい？
- 新規セッションで直前のリポジトリを参照したりする
- 最終的にマルチワークスペースをやめることで対処した（対症療法でしかない）
- 異なるコンテキストのマルチな作業がしにくいなって
- 今更感満載だけど、一度にたくさん作業させるぜ、には向いてないかも
- リポジトリ毎に同じような作業をさせたい時はスキル化するべきか
- VS Code で開きはするんだけど、操作の大半が AI に向いていて、IDE としての VS Code の使い方を忘れがち

## AI

- メインは claude サブは codex あと Copilot 稀に jules と gemini
- 強課金していないので全部ちょっとずつかじらせてる
- 強課金して特定の AI やモデルのファイル構造やサブツールの使い方にロックインしたくないため
- Copilot だけ VS Code Chat から呼び出し。それ以外はターミナルから指示出し。専用デスクトップアプリ類は入れてない
- しがないフリーランスなので、どれを使うにしても対応に困らない程度に勉強しておく必要がある、くらいの
- 難点はこれら AI ツールの作成するファイル類をリポジトリに含めない（AGENTS.mdとかは入れてある）ようにしているところ
- GitHub Copilot の Squad とか init しただけで20ファイルくらい出してくるんだけど、中身の確認なんてしてられないじゃない？
- AI のコードレビューすら手抜きしようって時代にツールの初期ファイルの確認なんてしてられない
- ファイルを作るのはいいけどコミットには含めないように gitignore や exclude に追加して、とかは面倒だった
- 同様にスキルは活用できてないので、そのうち再検討する予定
- そういえば、最近サブエージェント使わないほうがいい、みたいなの流れてたよね。ぶっちゃけ高性能モデルをがんがん使えるならそうだよね、としか。。。

## AI に任せっぱなしにするべきじゃないよねって

- AI を第三の認知系統とする System 3 先日の qiita のイベントの発表にも出てた
- お口の悪い人は認知的降伏をバカになると表現
- Obsidian 等のセカンドブレインに AI を追加すると加速するわな
- 覚えておかなくても経験しなくてもなんならまったく知らなくてもAIが教えてくれる
- AI の言いなりってゆうか、AI に任せていいところと悪いところの線引きをどの辺に置くかの話
- 判断は人間がする必要がある
- 判断の根拠を人間側でちゃんと握れないと、判断すらAIに任せることになる
- 判断じゃなくて脳死してないか、は常に自問自答したい

## AI のコードを眺めながら

- 同じものを手書きできるか

- 知識や機能ではAIには勝てない

# こうしておけばよかったと（あとになって）思うこと

または次からはこうしようと考えたこと。次のプロジェクトを始める前に読み直す用。

## 自動化を最優先

- prek は当然
- 言語ごとのフォーマッターとリンターを追加（今回は後回しになって後々だるくなった）
- テストのSMLとかe2eとか
- （結局人が目視確認するテストも欲しいんだよなぁ　みつを）
- prek と自動テストが通っているなら最悪コードを読んでなくてもなんとかなる（汚いコードは後で直せる）
- 自動化による開発ループと、その出口としての prek が機能すれば安心して作業ができる
- 設定はいったんクリーンにして、ignore や exclude は都度後づけしたほうがよさげ（それ自体が判断としてリポジトリに残る）

## 手直しを前提とする

- 業務では困るかもしれないけど
- 個人開発のツールは動いているだけでえらいのだから
- バグが出たら直せばいい。対応するテストを追加すればなおよし
- とにかく早くたくさん動かす
- AIはモデルを決めてだいたい同じ結果になるようにしたほうがいいかも（しょっちゅう新しいモデルがでるからなぁ）

## 作業記録

- ADR を残すようにする
- 仕様とは別に、取捨選択の記録を残しておくといいかも
- とくに選択しなかった理由を書いておくと、あとで見直した時に解消していれば選択肢が広がる
- さきにも書いたが今は aqua をバージョン管理ツールのメインに置いている。dependabot の [この issue](https://github.com/dependabot/dependabot-core/issues/12320) から [この PR](https://github.com/dependabot/dependabot-core/pull/14500) が通ったら mise メインに切り替えるかもしれない
- ちなみに [prek 対応の issue](https://github.com/dependabot/dependabot-core/issues/14624) が通るまで `prek.tomi` にしないで `.pre-commit-config.yaml` を使うことにしている
- 良し悪しではなく dependabot でも対応しています、が広範囲・高レイヤーに対して説得力があると考えているから
- みたいなことを ADR に書いて残しておくと、来年見た時にじゃあ再検討しようか、としやすい

## 言語選択

- 今回は terraform ユーザー向けのツールだったこともあり、半分脳死で Golang を選択した（terraform も Golang で書かれている）
- 外部ツールだし、依存的にはまったく関係がないので別の言語でもよかった。だけど terraform をいじってる人の多くは Golang の環境を持っていることが多い（持ってるよね？手元で go build できるよね？）ので、受け入れやすいかもしれない、という目算
- Golang のほうが見慣れていて、AI にコードを書かせてもまだ読めるだろうってのもある
- テストで1万ファイルくらい一度に処理をさせたところ、さすがに20秒くらいかかってしまった
- 性能面でいえば Golang よりも Rust のほうが（書き方の違い？）走査力が高いのかもって思った
- 気が向いたら勉強がてら tfstyrust って名前で Rust 版を作ってもいいかもしれないとか
- 要は AI 時代にツールの言語選択はより判断力が必要になるなって

## その他雑多なこと

- 競合調査はもう少しちゃんとしてもよかった
- 周辺ツールや競合についての調査レポートを作成させる、とかは AI にやらせるべき仕事じゃないか
- フォーマッターやリンターの中を調査する時間とってもいいかなとか
- markdown は rumdl を使ってるし、yaml は ryl を使っているけど、手持ちのファイルを通す程度しか見てない
- なぜそういうルールがあるのか、なぜそのルールに従うのがいいのか、はツールのドキュメントとにらめっこが要るなって
