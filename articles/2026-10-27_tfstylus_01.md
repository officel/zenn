# tl;dr

- [terraform のコードを少し整える tfstylus を作ってみた](https://zenn.dev/terraform_jp/articles/2026-10-26_tfstylus) の続き
- 今回はなぜこのツールを作ったのか、について

# なぜ作ったのか

- AI全盛期とも呼べる2026年現在、AIが書いたコードの中身を読まない、PRのレビューをしない、コードの綺麗さや可読性は重要視されない、そんな時代へのアンチテーゼ（言ってみたかっただけ）
- まぁやってみたかったから、以外の何者でもないんですけれども

# やってみたかった

## 個人開発をやってみたかった

- なにもかもをAI任せにする時代に、何がどこまでできるだろうか
- 個人的に常にスキルアップをしていないと、時代に飲み込まれてご飯食べられなくなっちゃう
- しがないフリーランスの身分でございますので、名刺代わりのプロダクトがずっと欲しかった
- 運用維持管理保守開発を継続できるほど余力があるわけでもない
- AIと並走してなら何かできるかも？

## モバイルアプリを作ってみたが飽きた

- 春に MacBook を購入したので、React Native + expo でモバイルアプリを作った（未公開）
- 作っただけで満足してしまった（絶賛放置中）
- NumberSum ってゲームのクローン
- 問題作成、回答、既存の問題を入力して回答まで自動でできるところまで組んだ
- 友人知人にはリリースすればいいじゃんと言われた
- ぶっちゃけクローンアプリをリリースするほどツラの皮が厚くなかった
- といえばかっこいいかもしれないけど、実際はクローン元と同じものでしかないならリリースする意味がないなって
- つまり作って満足したので飽きた（から放置されてる）
- それって外から見たら何もやってないのと変わらない

## 実は

- 経歴だけは長い（もう30年以上業界にいる）けど、技術力はそれなりでしかない
- いろいろできる自負はもちろんあるけど、あくまでどれもそれなりｗ
- 専門行程のエンジニアには太刀打ちしようもない
- ただの目立ちたくない陰キャなんだけど、本当のところはたいしたことできない自分ってのが露呈するのが嫌だった（バレてるところにはバレてるわけだけれどもｗ）
- このまま何もしないで、何も残さないで終わっていいのかなって（急にマジなトーンｗ）
- 素人さんがバイブコーディングとか言ってアプリ作る時代に、専業エンジニアがAI使ってツールのひとつも作れなくてどうするって話なわけよ
- というわけでようやく重い腰をあげて一念発起したってワケ

## やるなら自分が一番使うものを作るべき

- どうせ作るなら自分が一番のユーザーで、使っていて満足するものを作らないといかん
- コストがかからないものがいい（モバイルアプリはデベロッパー登録等でお金かかるしね）
- terraform しかないじゃないか（もう10年くらいインフラ／SRE業をしていてterraformとは2018年からの付き合いだ）
- Golang で CLI な OSS なら、お金かからないし、自分が一番使うし、好きに作っていいじゃないかと
- 何年か前に cobra で作った Golang のツールは公開もしてないし、自分でも使ってないし、一からやり直しかな
- でも terraform 向けツールなんてたいていのものがあるよね
- そんな時は ISSUE から始めよ（みんな読みましたか？）
- terraform のコードって、人によってちょいちょい書き方違うし、後付けしたりするので整ってないんだよね
- 自分で書いたやつだって時間経過や目的によって、書き方や順序が整ってないのがたくさんある
- 統一したいな
- もちろんポリシー等である程度整えられるけど、ポリシーによって統一はされない（variable の desc を先頭に置けってポリシーと value を先頭に置けってポリシーは場所によって成立してしまう）
- editorconfig や prettier みたいに強制はしないけど、普段から使っていればある程度ルールにしたがって整う、みたいな感じがいいな
- とくにチームでコードを書いていると、勝手にいじれないところもあるはず
- 設定で処理をオンオフできればいいかも
- つまり適用するなら絶対にこうなる、だけを詰め込めばいける（んじゃないかなって）

## という感じで作り始めた

- 世の中ではAIになんでも丸投げとか、マルチエージェントで任せっぱなしとかあるけど、そんなにAIを使いこなせていない
- 以前 Golang の勉強用に作ったツールは [Jules - An Autonomous Coding Agent](https://jules.google/) を使って Issue ドリブンで作った
- ぶっちゃけ成長済のコードならともかく、イチから書く時はちょっとダルい
- 今回はちゃんと設計から相談しながら書いてみようということで、`AGENTS.md` を書いた後、`DESIGN.md` と `issues/` に設計要件を起こしてもらいながら、それを実装させる、という方式でやってみたってワケ（世間ではAI-DLCと呼ばれている手法のうっすい感じだと思ってもらえれば）
- 各種AIに、「こういう実装を検討したいのでissueにして」って頼んで、出てきた内容を精査して、「直して。不明点があったら聞いて」を繰り返して、「じゃあ実装して」の繰り返しでほぼやった
- テストも書いてもらったし、見直しも何回かやってもらって整理した
- PRのレビューやテスト内容についての確認や実際の動作確認、目視テストの作成等は自分でやった
- 一応形にはなってリリースまでこぎつけているので、そこそこうまくできたんじゃないかな

# まとめと次回予告

- たいしたことしてないまま終わりたくないロートルエンジニアがチート（AI）を使ってツールを作り始めた物語
- なにかやらなきゃと思いつつ、なにもできてないなって同志に届くといいな
- 次回「あたしって、ほんとバカ」
- 始める前にわかっていなかったことについて書く予定
